# concept-review

design.md や実装の PR が、docs/concept.md の意図から気づかないうちに離れていくのを防ぐ。
「3 原則を破っていないか」を毎回 concept.md を開いて確認する代わりに、このスキルが
チェック項目を固定して機械的に照らし合わせる。

## 使い方

対象を受け取る（PR 番号 / ブランチ名 / diff 本文 / 提案文のいずれか）。

```sh
gh pr view <番号> --json title,body,files
gh pr diff <番号>
```

### 1. 変更内容を要約する

対象が何を変えようとしているかを 2〜3 行で要約する。要約が無いと、どの観点が関係するか
判断できない。

### 2. 各観点について判定する

`references/concept-checklist.md` に concept.md から抽出したチェック項目が、原文の節番号
つきで整理してある（読み手が concept.md を開かずに済むように）。次の観点それぞれについて
**準拠 / 逸脱 / 該当なし** を判定し、根拠（concept.md のどの記述に基づくか）を 1〜2 行で示す。

- 3 原則（入力欄は常に 1 つ / ユーザーに設定を選ばせない / 詳細ページの仕事は次の作成者を作る）
- 合格基準（「LINE に直接打つより速いこと」）
- スコープ表（Phase 1 / 2 / 3 /持たない、のどこに位置づく変更か。Phase の先取りや「持たない」領域への侵入がないか）
- Phase 3 のために開けておく穴 3 点（owner の余地・発行者スロット・13 ヶ月上限の一本化）を壊していないか
- スパム対策 4 点（URL 自動リンクしない/本数制限・作成レート制限 IP+device・全ページ noindex+推測不能URL・通報導線）
- 保持ルール（最終イベント終了 +7日、下書きは作成 +7日、13 ヶ月上限）

### 3. 逸脱には推奨を付ける

逸脱が見つかったら、次のどちらかを推奨する。理由も添える。

- **設計書を直すべき**: concept.md の原則自体が古くなった、あるいは意図的な例外として明文化すべき
  変更（例: design.md §14.2-7 の Workers Paid 契約のように、逸脱を認めた上で concept.md に追記した前例がある）。
- **実装を直すべき**: 原則は今も妥当で、PR 側が意図せず外れている。

判断に迷う場合はどちらか一方に決めず、両方の選択肢と影響を提示してオーナーの判断に委ねる。

## 出力フォーマット

```
対象: <PR番号 / ブランチ / 提案名>
総合判定: 準拠 / 逸脱あり
変更内容: <2〜3行の要約>

| 観点 | 判定 | 根拠 |
|---|---|---|
| 3原則-1 入力欄は常に1つ | 準拠/逸脱/該当なし | <concept.md §01 のどの記述に基づくか> |
| 3原則-2 設定を選ばせない | ... | ... |
| 3原則-3 詳細ページ=次の作成者 | ... | ... |
| 合格基準 | ... | ... |
| スコープ表 | ... | ... |
| Phase3の穴 | ... | ... |
| スパム対策 | ... | ... |
| 保持ルール | ... | ... |

逸脱の推奨: <各逸脱について「設計書を直す」/「実装を直す」と理由。迷う場合は両方の選択肢と影響を書く>

オーナーの判断事項: <推奨が一方に決め切れない場合の選択肢と影響。無ければ「なし」>
次のアクション: <誰が・何を>
```

## 例

- 「詳細ページに『保存期間を選ぶ』トグルを追加する PR」→ 3原則-2（設定を選ばせない）に逸脱。
  concept §02 の「公開範囲・保存期間の設定」は明示的に「持たない」に分類されているため、
  実装を直す（トグルを外す）ことを推奨する。
- 「メモ欄の URL 数上限を 3 → 10 に緩める提案」→ スパム対策（URL 本数制限）に逸脱の可能性。
  design.md §9.2 の `MAX_MEMO_URLS = 3` の根拠（カレンダースパム対策、concept §09）を示した上で、
  緩めたい理由（正当なユースケースが弾かれている等）が実データに基づくなら設計書側の定数変更を
  検討し、根拠が薄いなら実装（提案）を見送ることを推奨する。
