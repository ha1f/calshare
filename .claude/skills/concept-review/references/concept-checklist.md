## §01 コンセプト — 3 原則と合格基準

> 予定を書くと、URLになる。渡された人は、ボタンひとつで自分のカレンダーに入れられる。

**3 原則**

1. **入力欄は常に1つ** — 1行でも、100行でも、将来的には PDF でも、同じ場所に入れる。
   チェック観点: 新しい入力手段（別のフォーム欄、設定パネル、複数ステップの入力）を追加していないか。
2. **ユーザーに設定を選ばせない** — 保存期間も、タイトルも、公開範囲も、黙って正解を出す。
   チェック観点: トグル・セレクトボックス・設定画面を新設していないか。「選択肢を1つ足すたびに
   ライトユーザーが減る」がこの原則の理由。
3. **詳細ページの仕事は、次の作成者を作ること** — 転換導線は、広告よりもカレンダー追加よりも
   上位に置く。チェック観点: 詳細ページに「自分も作る」より目立つ・優先度が高い要素を足していないか。

**合格基準**（作成動線の設計判断はすべてこれで決める）

> LINE に「9/20 19時 渋谷」と直接打つより速いこと。

チェック観点: 作成フローに新しいステップ・確認・待ち時間を足していないか。

## §02 スコープ

Phase 1（最初のリリース）/ Phase 2（数字を見てから）/ Phase 3（事業者向け有料機能）/
持たない（意図的に作らない）の 4 分類。

**持たない**（意図的に作らない。ここへの侵入は原則として逸脱）

- 出欠・コメント（調整さんの領域）
- 予約・受付機能（「配信はする、受付はしない」）
- アカウント必須化（ログイン不要が最大の武器）
- 公開範囲・保存期間の設定（原則2に反する）
- 匿名認証（Firebase/Supabase。編集トークンで代替済み）

**Phase 3 限定**（Phase 1・2 での先取りは原則として逸脱）

- パスワードロック（無料で出すとモデレーションの死角になる）
- 広告非表示・発行者ロゴ表示
- 無期限の保持（13ヶ月上限の解除）

**Phase 2 限定**（Phase 1 での先取りは要検討）

- 複数イベント（貼り付け・PDF・画像）
- webcal 購読
- ユースケース別テンプレページ
- Google ログイン

## §07 保持期間と上限（保持ルール）

- 保持期限は「**最終イベント終了 + 7日**」。ユーザーに選ばせない（原則2）。
- 日時が取れない下書きは「**作成 + 7日**」。
- 作成できるイベントの上限は「**13ヶ月先まで**」。課金の壁ではなく仕様上の制約（遠未来スパム対策、
  同時保持件数の上界の確保）。
- URL は推測不能なランダム文字列、`noindex`。
- 編集権限は作成時に発行した編集トークンを localStorage に保存（別端末では編集できない、既知の割り切り）。

チェック観点: 保持期間・上限をユーザーが設定できるようにしていないか。13ヶ月上限を単一の定数
以外の場所（複数の分岐）に広げていないか（§09 の Phase 3 の穴と表裏）。

## §09 コスト・収益・防御

### Phase 3 のために開けておく穴 3 点

B 向け機能は今は作らないが、後から乗せられるよう次の 3 点だけ用意しておく。

1. データモデルに **owner の概念**を入れられる余地を残す（Phase 1 では常に null）
2. 詳細ページに **「発行者」の表示スロット**を用意しておく（無料は空、有料はロゴが入る）
3. 上限は **13ヶ月の一本**にしておく（B 向けに「無期限」を後付けできる）

チェック観点: この 3 点以上に Phase 3 向けの分岐やコードを今から作り込んでいないか（「今のコードを
汚さない範囲で」という制約に反する）。逆に、この 3 点の余地自体を塞ぐ変更（例: owner 概念を
最初から使う実装、13ヶ月上限を複数箇所に分散させる実装）をしていないか。

### スパム対策は初期から（4 点）

- 説明欄の URL は**自動リンクしない**／**外部リンク数を制限する**
- 作成の**レート制限（IP ＋ デバイス単位）**
- **全ページ `noindex`**、URL は**推測不能**に
- **通報導線**を最初から置く

チェック観点: 新機能が URL・リンクを扱うとき自動リンク化していないか、外部リンク数制限
（design.md §9.2 の `MAX_MEMO_URLS`）を回避する経路を作っていないか、レート制限の対象外に
なる新しい書き込み系エンドポイントを作っていないか、新しいページ種別に `noindex` を付け忘れていないか。

## 該当なしにしてよいケース

上記いずれの観点にも実質的な影響が無い変更（内部リファクタ、テストの追加、typo 修正、
ログ出力の調整など）は、該当する観点だけ判定し、それ以外は一括で「該当なし」としてよい。
無理に全観点へコメントを付けない。
