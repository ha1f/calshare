# owner-task

「Issue を起票して終わり」にしない。土台（runbook・スクリプト・ワークフロー・スキル）を先に作り、
Issue に残すのはオーナーにしか押せない最小の操作と、オーナーにしか下せない最小の判断だけにする。
同じ作業が再発しても、次はスキルか自動化が先に動くようにする。

## 手順

### 1. 分解する

見つけた作業を 3 つに分ける。

- **エージェントが今できる土台**: 手順書（`docs/runbooks/`）、判断の記録フォーマット、判定ロジックなど、今すぐ書ける部分。
- **スクリプト / ワークフロー / スキルで仕組み化できる部分**: 決定的な処理（`scripts/`）、繰り返し実行する操作（`.github/workflows/`）、繰り返し必要になる判断の型（`.claude/skills/`）。
- **本当にオーナーにしかできない最小の判断・操作**: 支払い情報の入力、契約の承認、本人認証を伴う手続き（レジストラ、Cloudflare ダッシュボードでの初回操作）、法的責任を伴う承認、ブランド（サービス名・ドメイン）の決定。

判断に迷ったら「これはエージェントが完了させても法的・金銭的な責任がオーナーに残らないか」を基準にする。残らないなら仕組み化の対象、残るならオーナー作業。

### 2. 土台と仕組み化を先に作る

- 手順を `docs/runbooks/<topic>.md` に書く（自動化されていること・オーナーが行う最小の作業・判断が必要な事項・失敗したときの見方、の構成が読みやすい）。
- 決定的な処理は `scripts/` に置き、繰り返し実行する操作は `.github/workflows/` にする。
- 「監査する」「審査する」「レビューする」のように毎回同じ観点で判断する作業は、Issue にせず `.claude/skills/` にスキルとして仕組み化する（例: このリポジトリの `license-review` `security-audit` `legal-review`）。判断作業を一エンジニアが都度やるより、AI が毎回同じ基準で行うほうが安定する。ただし免責が要るもの（法務判断など）は免責を明示した上で「専門家に見せるべき論点」まで抽出し、判断を放棄しない。

土台が無いまま Issue だけ作らない。Issue の「オーナーに残る作業」は、土台を作った後に初めて「最小」になる。

### 3. Issue を作成・更新する

`assets/issue-template.md` の 4 見出し（準備済み / オーナーに残る作業（最小） / 判断が必要な事項 / 完了したら進むこと）で書く。ラベルは `owner help wanted`。

```sh
# 新規作成
gh issue create --title "[H<番号>] <作業名>" --label "owner help wanted" --body-file /path/to/body.md

# 既存 Issue の更新（土台ができて「残る作業」が減ったとき）
gh issue edit <番号> --body-file /path/to/body.md

# 状況を伝えるだけならコメントで十分
gh issue comment <番号> --body "provision.yml の zone_and_waf ジョブで自動化しました。残る作業は手順3のみです。"

# 完全に自動化できた場合はクローズする（理由を必ず書く）
gh issue close <番号> --comment "scripts/cf/ensure-waf-rate-limit.mjs と provision.yml の zone_and_waf ジョブで自動化したため、手動作業は不要になりました。"

# 一覧確認
gh issue list --label "owner help wanted" --state open
```

すでに Issue があるかを先に確認する（重複を作らない）。

```sh
gh issue list --label "owner help wanted" --search "<キーワード>"
```

Issue の作成・更新・クローズは、このリポジトリではエージェントが行ってよい（マージまで任されている）。クローズするときは理由コメントを必ず添える。

### 4. 複数の Issue にまたがるときはチェックリストにまとめる

公開に向けて複数の H 番号が関係するときは、個別 Issue を作った上で「公開までのチェックリスト」
Issue を1つ作り、順序付きで各 Issue にリンクする（依存関係がある場合は順序を明記する）。
このチェックリストの機械的な部分は `go-live-check` スキルが自動で拾える（GitHub Secrets・Variables・
`owner help wanted` の open 状況など）。手動で全部を書き下ろす前に `go-live-check` を走らせて土台にする。

## 出力フォーマット

チャットで報告するときは、次の順で簡潔にまとめる（詳細は Issue 本文に書く）。

```
作業: <作業名>（design.md §13 の H<番号> 等）
分解:
  - 土台: <作った runbook / 記録フォーマット>
  - 仕組み化: <作った scripts / workflow / skill、または「無し（判断作業のため）」>
  - オーナーに残る最小の作業: <1〜3行、実行可能な粒度>
Issue: #<番号>（新規作成 / 更新 / クローズ） <URL>
オーナーの判断事項: <選択肢と影響。無ければ「なし」>
次のアクション: <オーナーが最初にやる1手順>
```

## 例

`references/examples.md` に、このリポジトリで実際に行った H1〜H14（design.md §13）の分解例をまとめてある。
「支払いが絡む契約」（H2）、「本人認証が要るレジストラ操作」（H3）、「完全に自動化できて Issue をクローズできる例」（H13）、
「土台はあっても実機と人でしか確認できない例」（H14）のように性質の異なるものを並べてあるので、
新しい作業を分解する前に、性質が近い例を読むと粒度が揃う。
