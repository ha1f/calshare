# 分解の例: docs/design.md §13 の H1〜H14

design.md §13「人間（リポジトリオーナー）にしかできない作業」に挙がった 14 件を、実際にこのリポジトリで
どう分解したかの記録。それぞれ `owner help wanted` ラベルの Issue（#2〜#15）が対応する。
`docs/runbooks/` があるものはそこに詳細な手順があるので、ここでは分解の型だけを要約する。
`docs/runbooks/` が無い環境でこのファイルを読んでいる場合は、この要約のみを参照する。

性質が大きく違う 4 件（H2・H3・H13・H14）を先に読むと、分解の粒度がつかみやすい。

## H13: Cloudflare WAF のレート制限ルール作成（完全に自動化できた例）

- **土台**: `docs/runbooks/custom-domain.md`（存在すれば読む）に手順を記載。
- **仕組み化**: `scripts/cf/ensure-waf-rate-limit.mjs` が `/api/*` へのレート制限ルールを冪等に作成し、
  `.github/workflows/provision.yml` の `zone_and_waf` ジョブが `domain` 入力（または `PUBLIC_DOMAIN` 変数）
  を渡すだけで実行する。
- **オーナーに残る作業**: `Provision Cloudflare resources` を `domain` 付きで Run workflow するだけ。
  ダッシュボードでの手作業は不要になった。
- **教訓**: 「ダッシュボード操作でコードに乗らない」ように見える作業でも、Cloudflare API 経由で叩ければ
  ワークフローに落とせる。ダッシュボード UI しかない訳ではないかを先に疑う。

## H14: LINE 実機確認（土台はあっても人にしかできない例）

- **土台**: `docs/runbooks/line-device-test.md`（存在すれば読む。無ければ作る対象）に手順と「結果」記入欄を用意する。
  `go-live-check` スクリプトはこの「結果」欄が埋まっているかだけを機械的に検査する。
- **仕組み化**: できない。iOS/Android の LINE アプリでの実機タップ操作そのものは自動化の対象外。
  唯一できる仕組み化は「結果を記録するフォーマットを決めて機械検査できるようにする」ところまで。
- **オーナーに残る作業**: 実機で開いて確認し、runbook の結果欄に記入する。
- **教訓**: 仕組み化できない作業は無理に自動化を探さず、「記録フォーマットを固定して機械検査できるようにする」
  だけでも土台として十分意味がある。

## H2: Cloudflare アカウント作成 + Workers Paid 契約（支払いが絡む契約）

- **土台**: `docs/runbooks/provisioning.md` に全体フローと、Paid 契約前に provision を進めた場合に
  何が起きるか（D1/R2 作成は進むが OGP 生成は Free の CPU 上限で落ちる）を明記。
- **仕組み化**: 契約そのものは自動化できないが、契約前後の切り分け（`scripts/cf/check-token.mjs` など）
  は用意し、「契約したかどうか」を後工程が推測せずに済むようにした。
- **オーナーに残る作業**: Cloudflare アカウント作成と Workers Paid（$5/月）の契約承認。
- **判断が必要な事項**: concept.md の「無料枠のまま放置できる」からの意図的な逸脱（design.md §14.2-7）。
  承認後に concept.md へ追記する。

## H3: ドメインの DNS 移管とカスタムドメイン割り当て（本人認証が要るレジストラ操作）

- **土台**: `docs/runbooks/custom-domain.md`。
- **仕組み化**: ゾーン作成（`scripts/cf/ensure-zone.mjs`）と WAF ルール作成は provision workflow が行う。
- **オーナーに残る作業**: レジストラ管理画面でのネームサーバー変更（本人認証が要るため自動化不可）と、
  ゾーンが `Active` になった後の `wrangler.jsonc` への `routes` 追加 PR の作成・マージ。

## H4〜H8: provisioning.md にまとめて自動化した例

D1/R2 作成（H4）、API トークン発行（H5）、`RATE_LIMIT_PEPPER` 生成（H6）、通報 Webhook 登録（H7）、
フォントライセンス確認（H8）は、いずれも `docs/runbooks/provisioning.md` 1 本に手順をまとめ、
`.github/workflows/provision.yml` の各ジョブ（`resources` / `secrets` / `font`）が実処理を行う。
オーナーに残るのは「トークン発行という 1 回の手作業」（H5）と「workflow_dispatch の実行」（H4・H6・H7）
だけ。H8 はライセンス確認の責任自体は人間に残るが、判定作業は `license-review` スキルに委譲できる。

## H9: 初回デプロイ承認（公開判断そのもの）

- **土台**: `docs/runbooks/deploy.md`。`DEPLOY_ENABLED` が `false` の間は `deploy.yml` の `gate` ジョブが
  状態をジョブサマリに出すだけで、実際のデプロイ処理は一切走らない。
- **仕組み化**: `gh variable set DEPLOY_ENABLED --body true` の 1 コマンドに公開操作を閉じた。
- **オーナーに残る作業**: そのコマンドを実行する判断そのもの。これは仕組み化できない（意図的に）。
  `go-live-check` スキルで「今それを押してよい状態か」を先に機械確認できる。

## H10: 法的文言の承認（法的責任）

- **土台**: `docs/legal/*.md` にドラフトと施行日・運営者のプレースホルダを用意。
  `docs/runbooks/legal.md` にオーナーが記入する手順と、判断が必要な事項（運営者表記・管轄裁判所・
  未成年の扱い等）を「法的助言ではない」と明記した上でリストアップ。
- **仕組み化**: フォーマット検査スクリプト（`scripts/legal/checkLegalDocs.mjs`、存在すれば読む）が
  施行日・運営者の空欄、条番号の欠番、変更履歴表の有無を機械検査する。内容の妥当性は検査しない。
- **オーナーに残る作業**: プレースホルダへの記入と、内容そのものの確認（必要なら弁護士相談）。
- **教訓**: 「法的助言はできない」で思考停止しない。文言のドラフトと機械的な形式検査は AI が作り、
  オーナーには「内容を確認して承認する」という最小の判断だけを残す。

## H11: 通報の一次対応（継続的な運用判断）

- **土台**: `docs/runbooks/moderation.md`（存在すれば読む）に判断基準の例を明記。判断基準の中身は
  `moderation-triage` スキルと `docs/runbooks/moderation.md` にあるので、ここでは繰り返さない
  （通報件数のみでは非表示にしない。report-policy.md 第4条3項・design.md §9.4）。
- **仕組み化**: `.github/workflows/moderation.yml`（`workflow_dispatch`）が SQL の組み立てと実行、
  実行結果の Issue コメント記録までを行う。
- **オーナーに残る作業**: 通知を見て `action` と `page_id` を選び workflow を実行するだけ。
  「非表示にするかどうか」の一次判断はオーナーに残る（自動非表示のしきい値を設計上持たない、§9.4）。

## H12: 使用量監視（しきい値を超えたときだけ判断を求める）

- **土台**: `docs/runbooks/usage.md` に監視項目と込み枠の一覧、超過時の対応方針。
- **仕組み化**: `.github/workflows/usage-report.yml` が毎週自動実行し、しきい値超過時だけ Issue を作る。
  超過が無ければ Issue すら作らない。
- **オーナーに残る作業**: 通常は何もしない。超過時のみ Issue を開いて対応方針を選ぶ。
- **教訓**: 「毎回確認してもらう」ではなく「閾値を超えたときだけ通知する」形にすると、オーナーの
  作業がゼロに近づく。監視系のタスクは基本この形を目指す。

## H1: サービス名・ドメインの決定（ブランド判断、仕組み化できない）

- **土台**: design.md §14.2-1 に未決事項として明記。決まるまでの間は `calshare.example` の仮値で
  開発を進められるようにしてある（T1 の足場）。
- **仕組み化**: 決定そのものはできないが、決まった後に反映する作業は仕組み化した。
  `scripts/check-domain.mjs`（存在すれば読む）がドメインの取得可否を確認し、
  `scripts/apply-service-name.mjs`（存在すれば読む）が決定したサービス名・ドメインをリポジトリ内の
  該当箇所（`wrangler.jsonc` の `PUBLIC_ORIGIN` 等）に反映する。
- **オーナーに残る作業**: サービス名とドメインの決定・取得（支払いを伴う契約行為でもある）。決定後は
  上記スクリプトを実行するだけでよい。
- **教訓**: 仕組み化できない作業は無理に土台を厚くせず、「決まるまで開発を止めない仮値」を用意する
  ことが最大の貢献になる。
