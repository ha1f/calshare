---

calshare は匿名でページを発行できるため、通報の一次判断をオーナー1人の負担にしないことが目的。判断を放棄せず、推奨・根拠・リスク・実行コマンドまでを揃えて、オーナーが最後に「承認する/しない」だけ決められる状態にする。

## 入力の受け取り方

次のいずれかの形で通報情報を受け取る。

- Discord/SlackのWebhook通知本文（ページURL・理由・累計件数・同一送信元の有効ページ数が含まれる。docs/design.md §9.4）をそのまま貼ってもらう。
- D1の `reports` テーブルの該当行と `pages`/`events` の内容を直接見せてもらう（Cloudflareダッシュボードのスクリーンショット、またはクエリ結果）。

対象ページの実際のタイトル・場所・メモが分からない状態では判断しない。Webhook通知だけでは本文が200文字に切り詰められている（docs/design.md §9.4）ので、判断に必要ならD1の内容を追加で求める。

根拠に引用する文言は、受け取った入力に実在するものだけにする（入力に無い文言を記憶や推測で補って引用しない）。メモが途中で切れている場合、見えている範囲だけで禁止事項に明確に該当するなら判定してよいが、根拠欄に「メモはN文字で切れている」と明記する。見えている範囲だけでは判断材料として足りなければ、迷わず判断保留にしてD1の全文を求める。

## 手順

1. **禁止事項に照らす**: `docs/legal/report-policy.md` があれば第5条の10項目、無ければ `docs/concept.md` §09（フィッシング・カレンダースパム・個人情報・レート制限回避）と `docs/design.md` §9.4 を基準にする。該当する条項番号を明示する。**条項は通報理由（`reason`）ではなく実際の内容で選ぶ**（例: 通報理由が「スパム」でも内容がフィッシングなら第5条1号を引く）。理由と内容が食い違うこと自体は根拠欄に1行書けば足り、それ以上の扱いは不要（第4条2項は内容の該当性を要件にしている）。`report-policy.md` の施行日が未記入（未施行）の場合は、同じ条項番号を引きつつ「ポリシー未施行のため根拠は concept §09 / design §9.4」と併記する。
2. **典型パターンと照合する**: `references/patterns.md` の「非表示に傾ける要素」「維持に傾ける要素」を両方あてはめる。片方だけを見て判断しない。
3. **同一送信元の状況を確認する**: 通報対象ページの `creator_ip_hash`/`creator_device_id` と一致する他の有効ページ数（Webhook通知に含まれる、またはD1で `PageRepository.countActiveByCreator` 相当のクエリ）を見る。件数が多いほど機械的スパムの確度が上がる。**一括非表示を推奨する前に、同一送信元の他ページのタイトルを確認する**（`node scripts/cf/moderation-sql.mjs --lookup --page-id <id>` で送信元を特定した上で、D1 の該当ページ一覧をオーナーに貼ってもらう）。他ページの内容を確認できないときは、推奨を「対象ページのみ非表示 → 他ページの一覧確認後にあらためて一括判断」の2段階に分ける（references/patterns.md は「同一送信元でも各ページを個別に見る」としており、内容を見ずに一括推奨まで進めるのはこの原則と矛盾するため）。
4. **通報件数・理由の妥当性を見る**: `report_count` と通報理由が実際の内容と符合するか。件数だけで判断しない（docs/legal/report-policy.md 第4条3項）。
5. **誤検知・見逃し双方の副作用を書く**: `references/patterns.md` 末尾の「副作用のバランス」を使い、この判断を誤った場合に何が起きるかを両方向で書く。
6. **推奨を決める**: 「非表示（このページのみ）」「非表示（同一送信元を一括）」「維持」「判断保留（追加情報が要る）」の排他4値から1つだけ選ぶ（2つを組み合わせて書かない。一括非表示を段階的に進めたいときは手順3のとおり2段階の推奨に分ける）。根拠が薄い・内容が確認できない場合は迷わず「判断保留」にする。
7. **実行コマンドを出す（実行はしない）**: `.github/workflows/moderation.yml` が存在すれば、次の形で起動コマンドを示す。ワークフローは実行前に対象件数を確認し0件なら更新せず停止すること、実行結果を Issue「[運用] 通報対応ログ」にコメントとして記録することを1〜2行で添える（詳細手順は `docs/runbooks/moderation.md`、存在すれば読む）。

   ```sh
   gh workflow run moderation.yml -f action=hide -f page_id=<id> -f note="<判断理由の要約>"
   # 一括非表示の場合
   gh workflow run moderation.yml -f action=hide-by-creator -f page_id=<id> -f note="<判断理由の要約>"
   ```

   ワークフローが無ければ、代わりにCloudflareダッシュボードのD1コンソールで実行するSQL（docs/design.md §9.4 に一括非表示のSQL例がある）を案内する。

8. **オーナー承認を待つ**: 実行コマンド・SQLはどちらも提示するだけに留め、オーナーが明示的に「実行して」と言うまで `gh workflow run` を自分で叩かない。承認が得られたら実行し、結果（起動したrun IDなど）を報告する。

## 出力テンプレート

```
## moderation-triage: <ページID or URL>

### 推奨アクション
非表示（同一送信元を一括）

### 根拠
- 禁止事項: docs/legal/report-policy.md 第5条3号（カレンダースパム）
- メモ欄に短縮URLが2本、タイトルに「本日中に確認」の緊急性文言
- 同一送信元（device_id一致）で過去1時間に有効ページ12件（典型パターン: 同一送信元からの大量作成）。他11件のタイトルも確認済みで、いずれも同様のカレンダースパム
- 通報理由「スパム」と内容が一致

### リスク
- 誤検知した場合: 正当な利用者のページを消してしまう可能性は低い（同一送信元12件、他ページも内容確認済み）
- 見逃した場合: カレンダースパムとして拡散が続き、ドメインレピュテーションが下がるリスク

### 実行コマンド
gh workflow run moderation.yml -f action=hide-by-creator -f page_id=abc123defg45 -f note="カレンダースパム、同一device_idで12件"
（moderation.yml が無い場合: docs/design.md §9.4 のSQLをCloudflareダッシュボードのD1コンソールで実行。実行前に対象件数確認、実行後は Issue「[運用] 通報対応ログ」に記録される）

### オーナーの判断事項
承認する操作: 上記の実行コマンドをそのまま実行する
承認しない場合の代替: 対象ページのみ `hide`（一括非表示は見送る）

### 次のアクション
オーナーが上記コマンドの実行を承認し次第、このセッションが実行して run ID を報告する
```

「判断保留」のときも同じテンプレートを使い、推奨欄に「判断保留（追加情報が要る）」、リスク欄の代わりに「不足している情報」を書く。同一送信元の他ページを確認できず2段階の推奨にする場合は、推奨欄に「非表示（このページのみ） → 他ページ確認後に一括判断」と明記し、「次のアクション」に他ページ確認の依頼を書く。
