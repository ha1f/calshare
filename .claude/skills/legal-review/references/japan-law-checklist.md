# 日本法チェックリスト

legal-review の「(b) 日本の法令の観点」で参照する。各項目は「なぜ問題になるか」「規約でどう書けばよいか（文例）」「弁護士に見せるべきか」の3点を持つ。文例はそのまま貼れる完成品ではなく、docs/legal/*.md の実際の条文と実装事実（design.md）に当てて調整する叩き台として使う。

## 1. 個人情報保護法

**なぜ問題になるか**: calshare は IP ハッシュ・device Cookie・通報者情報・予定ページの本文（design.md §3.1, §9.6）を取得する。個人情報保護法は「取得する情報の明示」「利用目的の特定・通知/公表」「第三者提供の制限」「委託先の監督」「開示等請求への対応」を求める。氏名・住所等が予定本文に紛れ込む構造（concept §09）なので、「個人情報を取得しない」と言い切れない設計であることが前提。

- 取得する情報の明示: 何を取得するか（IPハッシュ、Cookie、予定本文、通報情報、アクセスログ）を列挙する。design.md §9.6・§3.1 の「残す/残さない」表と一致させる
- 利用目的: 「サービス提供」「不正利用対策」のような抽象語だけでなく、レート制限・通報対応・不具合調査のように具体的に書く（利用目的の特定義務）
- 国内の第三者提供: Cloudflare（Workers/D1/R2）は個人情報保護法上「委託」に整理するのが一般的（27条5項1号。提供先の監督義務は生じるが、本人同意は不要）。Discord/Slack への通報通知は、通知内容が「個人情報」に当たるか（通報対象ページの URL・理由・件数中心で、通報者本人を特定する情報を含まない設計なら該当性は低い）を確認する
- **外国にある第三者への提供（28条。要確認: e-Gov で現行条文を確認）**: 国内の委託は同意不要でも、委託先が外国にある場合はこの例外は使えず、28条が別途適用される。委託先が個人情報保護委員会規則に定める基準に適合する体制を整備している事業者に当たるか、または本人同意を取るか、あるいは移転先の国・地域を本人に明示するかのいずれかが要る。Cloudflare は米国法人で D1/R2 の保管場所も国外になりうるため、privacy.md でこの整理を明示できているかを確認する。**弁護士に見せるべきか: 要確認**（Cloudflare の体制適合性の該当性判断は個別の実務判断を要する）
- **外的環境の把握**: 個人情報保護委員会の通則編ガイドラインは、安全管理措置の一環として外国で個人データを取り扱う場合の「外的環境の把握」（取扱う国・地域の制度等の把握と、必要な安全管理措置の実施）を求め、これを本人が知り得る状態に置くことを含む。D1/R2 のデータ保管国（Cloudflare のリージョン）を privacy.md の公表事項に含めるかを確認する。**弁護士に見せるべきか: 要確認**（Cloudflare 側の実際の保管国の確認と、公表の粒度の判断を要する）
- **IP ハッシュ・device Cookie の位置づけ**: 単体では特定の個人を識別できないため「個人関連情報」（個人情報保護法上、個人情報とは別のカテゴリ）に留まる可能性があるが、予定ページの本文（氏名等が書かれた場合）や通報記録と紐づいて特定の個人を識別できる状態になると「個人情報」に当たりうる。privacy.md がこの区別を意識した書き方になっているかを確認する。**弁護士に見せるべきか: 要確認**（個人関連情報／個人情報の該当性は事例ごとの判断を要する）
- 保存期間: design.md §3.2 の保持期限（最終イベント+7日等）をそのまま明記できる
- 開示等の求めへの対応窓口が無いことの書き方: 「対応窓口を設けていない」と正直に書いた上で、代替手段（利用者自身の編集機能での訂正・削除）を示す。窓口が無いこと自体は違法ではないが、法が求める「保有個人データに関する事項の公表」（取得目的・安全管理措置の概要等、外的環境の把握を含む）は最低限必要
- **弁護士に見せるべきか（全体）**: 基本的な公表事項の書き方は定型化されているため通常は不要だが、上記の外国第三者提供・外的環境の把握・個人関連情報の該当性の3点は個別の実務判断を要するため要確認とする。「開示請求が来たときに実際にどう対応するか」の運用フローを詰める段階でも確認が望ましい

## 2. 電気通信事業法の外部送信規律（第27条の12）

**なぜ問題になるか**: 2023年改正で、Cookie 等を用いて利用者情報を外部に送信する場合、その内容を通知または公表する義務が新設された（対象事業者の範囲・除外規定あり）。calshare は `cs_device` Cookie（design.md §9.3）を発行し、将来的に広告（concept §09 Phase 2/3のディスプレイ広告・アフィリエイト）を導入する計画がある。

- 現状（Cookie は自社のレート制限用途のみ、外部送信なし）の書き方: 「本サービスが発行するCookieは端末識別のためのものであり、外部の事業者に送信しません」と明記できる
- Cloudflare のログ: Cloudflare 自体はホスティング基盤（委託先）であり、Cookie 情報を外部の広告事業者等に送信しているわけではない前提なら、外部送信規律の直接の対象にはなりにくい。ただし Cloudflare Analytics 等の追加機能を有効化した場合は再検討が必要
- 将来の広告導入時: 広告配信事業者のタグ（Google AdSense 等）を埋め込むと外部送信規律の対象になる可能性が高い。導入前に規約・プライバシーポリシーの改定が必要になることを、未決事項として残しておく
- **弁護士に見せるべきか**: 現状（自社Cookieのみ）は不要。広告タグ導入時は要確認（対象事業者の該当性・公表事項の要否を個別に判断する必要がある）

## 3. 特定商取引法

**なぜ問題になるか**: 通信販売等で消費者と取引する場合、事業者の氏名・住所・電話番号等の表示義務がある。calshare は Phase 1・2 は無料・決済なし（concept §02, §09）なので**現時点では表示義務が無い**。Phase 3 で課金機能（パスワードロック等）を始めると義務が生じる。

- 現状の書き方: 規約に特定商取引法の表記を置く必要はない。ただし「本サービスは本規約の施行時点では課金を行いません」のように、将来課金する可能性と、その際は規約を改定する旨を明記しておくと整合が取れる（terms.md 第11条の「広告」と同じ書き方をコピー可能）
- Phase 3 移行時に必要になる項目（先出しで洗い出しておく）: 販売事業者の氏名または名称、住所、電話番号、代表者名、販売価格、支払時期・方法、役務の提供時期、返品・キャンセルの可否と条件、動作環境。個人事業主の場合は住所・電話番号の公開が必要になる点がオーナーの負担として大きい（個人開発者が特商法表記を嫌う典型的な理由）
- **弁護士に見せるべきか**: 現状は不要。Phase 3 の課金設計が固まった段階で、特商法表記の文面は弁護士確認が望ましい（住所非公開の代替手段の可否等、実務判断が絡むため）

## 4. 消費者契約法

**なぜ問題になるか**: 消費者契約法第8条（要確認: e-Gov で現行条文を確認）は、事業者の損害賠償責任を「全部免除」する条項を、過失の程度を問わず無効にする（1項1号・3号）。軽過失（通常の過失）であっても全部免除は無効。許されるのは、軽過失の場合に限って賠償額の上限を定める「一部免除」だけ。故意・重過失について一部免除する条項も無効（2号・4号）。さらに2023年6月施行の8条3項により、その一部免除が軽過失の場合にのみ適用されることを条文上明示しない書き方（「法令で許される限り」等）も無効になった。calshare の利用者は事業者だけでなく個人も含むため「消費者契約」に該当しうる。terms.md の免責条項（第13条）のような「一切責任を負わない」という書き方は、軽過失による損害を含めて全部免除しようとすると無効リスクが高い。

- 問題になりやすい文言: 「運営者は一切の責任を負いません」「運営者の故意または重過失による場合を除き…賠償する責任を負いません」のように、軽過失の場合の責任を全部免除する書き方（後者も「軽過失なら全部免除」という点で無効リスクが高い。故意・重過失を除外しただけでは足りない）
- **規約でどう書けばよいか（文例）**: 「運営者の軽過失による場合、賠償責任は〈上限〉を限度とします。故意または重過失の場合はこの限りではありません」のように、**軽過失のときに限って上限を定める一部免除**にし、その一部免除が軽過失限定であることを条文上明示する（8条3項）。無料サービスで上限額を何にするか（直接かつ通常の損害に限る、利用者が支払った対価を上限にする等）は判断が分かれるため、**弁護士に見せるべき論点**として残す
- **弁護士に見せるべきか**: 上限額の設定と文言は消費者契約法第8条・第10条（信義則に反して消費者の利益を一方的に害する条項の無効）に触れやすい典型論点なので、**最終的な文言は弁護士確認が望ましい**。ここでのレビューは「全部免除になっていないか」「軽過失限定が条文上明示されているか」の一次チェックに留める

## 5. プロバイダ責任制限法 / 情報流通プラットフォーム対処法

**なぜ問題になるか**: 2024年成立の情報流通プラットフォーム対処法（旧プロバイダ責任制限法を改称・拡充）は、大規模プラットフォーム事業者に削除申出への対応の迅速化・体制整備等を求める（適用対象規模の該当性は要確認）。calshare の規模では直接の適用対象にならない可能性が高いが、匿名投稿サービスとして「削除依頼」「発信者情報開示請求」への対応方針は運用上必要。

- 削除依頼への対応方針の書き方: report-policy（通報ポリシー）に、通報を受けた場合の対応（design.md §9.4: 運営者が個別に判断し非表示にする。自動非表示のしきい値は設けない）をそのまま記載する
- 発信者情報開示請求への対応: calshare は生IPを保存しない設計（design.md §9.3, §9.6）なので、「開示すべき発信者情報（生IP等）をそもそも保有していない」ことを明記できる。これは開示請求への実務的な回答にもなる重要な設計上の事実で、terms.md / privacy.md のどちらかに明記すべき
- **弁護士に見せるべきか**: 適用対象規模に該当するかの判定と、実際に削除依頼・開示請求が来た場合の個別対応は弁護士確認が必要。規約への記載レベル（対応方針の一般的な明記）は不要

## 6. 著作権・商標（ユーザー投稿の権利帰属）

**なぜ問題になるか**: 利用者が入力したタイトル・メモ等（著作物性が認められる場合がある）について、運営者がサービス提供上必要な範囲（表示、OGP画像生成、ics生成）で利用できることを明確にしておかないと、運営者の利用行為が著作権侵害と評価されるリスクが理論上ある。

- **規約でどう書けばよいか（文例）**: 「利用者は、本サービスに入力した内容について、本サービスの提供（予定ページの表示、カレンダー連携用ファイルの生成、SNS等でのプレビュー表示を含みます）に必要な範囲で運営者が利用することを許諾するものとします」。著作権を運営者に「譲渡」させる必要はなく、利用に必要な範囲のライセンスで足りる
- 商標: 利用者が入力したタイトル等に第三者の商標を含めても、通常の予定告知としての利用は商標的使用に当たらないことが多いが、詐称・なりすまし目的の利用は禁止事項（terms.md 第8条 → report-policy.md）でカバーする
- **弁護士に見せるべきか**: 不要。この程度の利用許諾条項は定型的

## 7. 未成年

**なぜ問題になるか**: 未成年者が法定代理人の同意なく締結した契約は取り消せる（民法第5条）。calshare はログイン不要・無料なので「契約」性は薄いが、無料サービスの利用規約についても未成年保護の観点で言及しておくのが実務上一般的。

- **規約でどう書けばよいか（文例）**: terms.md 第14条のように「保護者の同意を得た上で利用してください」と案内する書き方で足りる。年齢確認の仕組みを持たない設計（design.md にログイン機能なし）と整合させる
- **弁護士に見せるべきか**: 不要。無料・非会員制サービスでは定型的な案内で足りる

## 8. 準拠法・管轄

**なぜ問題になるか**: 準拠法・合意管轄を定めておかないと、紛争時にどこの裁判所で争うかが不明確になる。

- **規約でどう書けばよいか（文例）**: 「本規約の解釈にあたっては日本法を準拠法とします」「本サービスに関して紛争が生じた場合には、（オーナーの住所地を管轄する地方裁判所）を第一審の専属的合意管轄裁判所とします」。「専属的合意管轄」を付けないと、専属性のない単なる管轄合意になり、相手方の住所地等でも提訴されうる
- **弁護士に見せるべきか**: 不要。定型条項

## この一覧の使い方

各項目は「現状（Phase 1・無料・ログイン無し）でどこまで必要か」と「Phase 2/3 で必要になる項目」を分けて書いている。legal-review の出力テンプレートでは、現状の docs/legal/*.md にこの一覧の指摘を当てはめ、重要度（高 = 法令違反リスクが具体的にある / 中 = 実務上望ましい / 低 = 将来のフェーズで検討）を付けて報告する。
