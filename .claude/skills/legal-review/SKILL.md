# legal-review

docs/legal/*.md を、実装の事実・日本法・文書間整合の3方向から審査する。Issue を切って終わりにせず、オーナーが承認できる形（総評・不一致・指摘・修正案）まで作り込む。

> **これは法的助言ではない。** ただし、一エンジニアが目視で確認するより網羅的にチェックするための手順であり、判断を放棄するための免責ではない。法令観点の指摘には重要度と「弁護士に見せるべきか」を必ず添え、確認が要る論点は避けずに名指しする。

## 審査対象

`docs/legal/*.md`。calshare では `terms.md`（利用規約）・`privacy.md`（プライバシーポリシー）・`report-policy.md`（通報ポリシー、terms.md/privacy.md から参照される。存在しなければ下記「docs/legal/ が無い場合の動作」に従う）を想定する。**docs/legal/ 配下のファイルは他エージェントが作業中のことがあるため、このスキルは読むだけで編集しない**。修正案は「差し替え文」としてチャット上に出し、適用はオーナーまたは担当エージェントに委ねる。

## 審査の3方向

### (a) 実装の事実との照合

`docs/design.md` の該当箇所を根拠にする。

- **§3 データモデル**: 保持期間の計算（§3.2）、編集トークンの扱い（§3.3）、変更バナー用スナップショット（§3.5）が、規約・プライバシーポリシーの記述と数値・挙動レベルで一致するか（例: 「7日で削除」の起点は「最終イベント終了から」か「作成から」か）
- **§7 カレンダー連携**: ics に URL を「[リンク]」へ置換する仕様（§7.2）、Google カレンダーリンクの details にメモの URL をそのまま載せる仕様（§7.2, 未決事項§14.2-5）は、プライバシーポリシーの「第三者提供」や利用規約の「URLの性質」の記述と矛盾しないか
- **§9 セキュリティ・スパム対策・プライバシー**: 取得する情報とログに残す/残さない情報（§9.6）、レート制限で使う IP ハッシュ・device Cookie（§9.3）、通報の Webhook 通知の内容（§9.4）が、プライバシーポリシーの「取得する情報」「第三者提供」条項と1対1で対応しているか。**設計書にある情報がポリシーに抜けている**、または**ポリシーに書かれているが設計書に根拠が無い**の両方向を確認する
- 実装コードが存在する場合はそちらも確認し、design.md との乖離自体も指摘に加える(設計変更が文書に反映されていない可能性があるため)

### (b) 日本の法令の観点

`references/japan-law-checklist.md` を使う。個人情報保護法・電気通信事業法の外部送信規律・特定商取引法・消費者契約法・プロバイダ責任制限法/情報流通プラットフォーム対処法・著作権/商標・未成年・準拠法/管轄の8項目を、現在の docs/legal/*.md の記述に当てはめる。**Phase 1(無料・ログイン無し)で必要な水準**と**Phase 2/3で必要になる水準**を混同しない(design.md の Phase 区分、concept.md §02 のスコープ表を参照)。

### (c) 文書間の整合

`terms.md` ⇄ `privacy.md` ⇄ `report-policy.md` の相互参照が実在するか、内容が矛盾していないかを確認する。

- 相互参照リンクが指す条文・ファイルが実在するか(存在しないファイルへのリンクは高優先度の指摘にする)
- 同じ事実(保持期間、通報の扱い、Cookie の用途等)を複数の文書で説明している箇所の数値・文言が一致しているか
- 「お問い合わせ窓口を設けていない」旨の記述が全文書で一貫しているか

## 出力フォーマット(固定)

```
これは法的助言ではない。一エンジニアの目視より網羅的に確認するための手順であり、判断は放棄しない。

## 総評
<レビュー対象の全体評価を2〜4行>

## 事実との不一致
<design.md のどの節と、docs/legal/ のどの条文が矛盾するか。無ければ「無し」>

## 法令観点の指摘(重要度つき)
<references/japan-law-checklist.md の各項目を当てはめた指摘。重要度: 高/中/低>

<terms.md/privacy.md/report-policy.md 間の矛盾・リンク切れ。無ければ「無し」>

<問題箇所の現在の文言 → 修正後の文言、を条文単位で提示>

<あれば列挙。無ければ「無し」とその理由>

## オーナーの判断が必要な事項
```

## docs/legal/ が無い場合の動作

`docs/legal/*.md` が1つも無い(またはこれから新規作成する)ときは、上記の審査フォーマットではなく、`docs/design.md` と `concept.md` の事実から「規約に書くべき事項の一覧」を出す。§3(データモデル)・§7(カレンダー連携)・§9(セキュリティ・スパム・プライバシー)・concept §09(スパム対策・課金方針)を読み、japan-law-checklist.md の各項目と突き合わせて、条文の見出し案と根拠(design.md の節番号)を列挙する。

## 進め方

1. `docs/design.md` の §3・§7・§9(必要なら §13・§14 も)を読み、事実を先に固める
2. `docs/legal/*.md` を全文読む(既存があれば)
3. `references/japan-law-checklist.md` を読み、8項目を1つずつ照合する
4. 固定フォーマットで出力する。**指摘だけで終わらせず、修正案の条文まで書く**。弁護士確認が要る論点は「なぜエンジニアの判断を超えるか」を一言添えて明示し、それ以外は自分で判定を出し切る
