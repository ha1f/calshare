# ライセンス別の義務一覧

審査対象のライセンスを SPDX 識別子に対応付けたら、このページで該当項目を引いて義務を列挙する。「義務」は判定書（assets/record-template.md）の該当項目にそのまま転記できる粒度で書いている。

表記の意味:

- **著作権表示**: 著作権者名を成果物または同梱ドキュメントに残す義務
- **ライセンス同梱**: ライセンス全文を配布物に含める義務
- **改変の明示**: 元から変更した事実を示す義務
- **名称の制約**: 元の名称・商標の使用を制限する条項
- **特許条項**: 明示的特許ライセンス／その撤回条件（パテントトロール対抗条項）
- **コピーレフトの範囲**: 派生物・結合物に同じライセンスを継承させる範囲
- **ネットワーク配信**: SaaS として配信するだけ（バイナリを配らない）でもコピーレフトが及ぶか
- **商用利用**: 商用利用の可否（列挙したものはすべて可。制限があれば明記）

## OFL-1.1（SIL Open Font License）

フォント専用ライセンス。calshare では Noto Sans JP（H8, design.md §11 OGP）で使う想定。

- 著作権表示: 元のライセンス本文（コピーライトヘッダ含む）をそのまま同梱すれば足りる。ただし配布物のライセンスファイルに著作権表示が含まれない場合（ライセンス本文だけの `LICENSE` 等）は、フォント本体の `name` テーブル（ID 0: Copyright 等）にある著作権表示を書き写したファイルを併せて同梱する
- ライセンス同梱: 必須。`OFL.txt`（または `LICENSE`）をフォントと一緒に配布する
- 改変の明示: サブセット化・字形の変更は「改変」に当たる。改変版も OFL でのみ再配布可能（コピーレフト）
- **名称の制約（Reserved Font Name, RFN）**: フォント名に RFN 宣言があると、改変版に同じ名前を名乗れない。サブセット化して配る場合はフォント内部名を変えるか、RFN が付いていないか確認する。Noto 系フォントは由来（Adobe の Source Han Sans 等）によって "Source" が RFN で "Noto" は RFN でない場合がある。要確認（フォント本体の `name` テーブルで個別に確認する）
- 単体配布の制限: フォント単体の販売は禁止。ソフトウェアの一部として（他の成果物と一緒に）配る分には無償・有償を問わず可
- 特許条項: 明示規定なし
- コピーレフトの範囲: フォント自体とその改変版（サブセット含む）。フォントを使って生成した画像・PDF 等の成果物には及ばない（OFL FAQ の一般的な解釈）
- ネットワーク配信: フォントバイナリ自体をブラウザに配信しなければコピーレフトの対象は「Workers 内で使うフォントファイル」のみ。ブラウザには生成後の画像（PNG 等）だけを返す構成なら、フォント自体の配布に該当するのはリポジトリ／R2 に置く行為
- 商用利用: 可

## MIT

- 著作権表示: 必須（著作権者名とライセンス全文をコピーに含める）
- ライセンス同梱: 必須
- 改変の明示: 規定なし（する義務はない）
- 名称の制約: 商標条項なし。ただし著作権者名を推奨や由来を偽る形で使うのは不可（一般則）
- 特許条項: 明示規定なし
- コピーレフトの範囲: なし（非コピーレフト）
- ネットワーク配信: 影響なし
- 商用利用: 可

## ISC

MIT とほぼ同一の非コピーレフトライセンス。義務も同じ（著作権表示・ライセンス同梱が必須、コピーレフトなし）。文言が簡潔なだけで実務上の扱いに差はない。

## BSD-2-Clause / BSD-3-Clause

- 著作権表示: 必須
- ライセンス同梱: 必須
- 改変の明示: 規定なし
- 名称の制約: **BSD-3-Clause のみ**「著作権者・貢献者の名前を宣伝目的で無断使用しない」条項がある（2-Clause には無い）
- 特許条項: 明示規定なし
- コピーレフトの範囲: なし
- ネットワーク配信: 影響なし
- 商用利用: 可

## Apache-2.0

- 著作権表示: 必須。加えて `NOTICE` ファイルがあれば、その内容を配布物に引き継ぐ義務がある（同梱される表示を消せない）
- ライセンス同梱: 必須
- 改変の明示: 改変したファイルにはその旨を明記する義務がある（コメントで「Modified」と書く等）
- 名称の制約: 商標・製品名・ロゴの使用許諾は含まれない（別条項で明示的に除外）
- **特許条項**: コントリビューターから明示的な特許ライセンスを受けられる。ただし利用者がそのソフトウェアに対して特許訴訟を起こすと、当該特許ライセンスが自動終了する（パテントトロール対抗条項）
- コピーレフトの範囲: なし（非コピーレフト。ただし改変ファイルの表示義務あり）
- ネットワーク配信: 影響なし
- 商用利用: 可

## MPL-2.0（Mozilla Public License）

ファイル単位のコピーレフト（弱いコピーレフト）。

- 著作権表示: 必須
- ライセンス同梱: 必須（ライセンス全文へのアクセスを提供）
- 改変の明示: 改変した「MPL 対象ファイル」のソースコードを、同じ MPL の下で開示する義務がある。ファイル単位なので、MPL ファイルを改変せずに同じリポジトリに置くだけの自作コードは MPL 化されない
- 名称の制約: 規定なし
- 特許条項: あり（コントリビューターからの特許ライセンス）
- **コピーレフトの範囲**: 「改変した MPL ファイル」に限定される（ファイル単位）。静的リンク・同梱しても、改変していない他のファイルやアプリ全体には及ばない
- ネットワーク配信: 配布（distribute）が起点で、SaaS として配信するだけで社外にソースを渡していなければ、MPL 自体は開示義務を発生させない（AGPL のようなネットワーク条項はない）
- 商用利用: 可

## LGPL-2.1 / LGPL-3.0

ライブラリ単位のコピーレフト（弱いコピーレフト）。

- 著作権表示: 必須
- ライセンス同梱: 必須
- 改変の明示: LGPL ライブラリ自体を改変した場合、その改変部分のソースを LGPL で開示する義務
- 名称の制約: 規定なし
- 特許条項: LGPL-3.0 のみ明示条項あり（GPLv3 と同様の枠組み）。LGPL-2.1 にはない
- **コピーレフトの範囲**: LGPL ライブラリ自体（と改変部分）に限定。npm パッケージを import するだけなら一般的に「動的リンク」に整理され、呼び出し側の自作コードは LGPL 化されない。ただし **calshare は wrangler（esbuild）で依存を単一ファイルにバンドルする**ため、実行時に動的にロードする通常の Node.js 環境と異なり「静的リンク相当」と解される余地がある。静的リンクと整理されると LGPL は「利用者がライブラリを差し替えられること」（リンク前オブジェクトの提供、再リンク手順の開示等）を求めるため、Workers/ブラウザ向けにバンドルする依存に LGPL のものが含まれる場合は、条件付き可と即断せず**弁護士確認の論点**として明示する
- ネットワーク配信: SaaS として配信するだけでは開示義務なし（AGPL ではない）
- 商用利用: 可（ただし利用者が LGPL ライブラリを差し替えられる手段の確保が求められる場合がある＝動的リンクを維持する実務的理由。バンドルする場合はこの手段を確保できるかが論点になる）

## GPL-2.0 / GPL-3.0

強いコピーレフト。**サーバサイドで動かすだけなら「配布」に当たらないため開示義務は発生しないのが原則**（GPL は配布時にソース開示を求める設計で、ネットワーク越しの利用そのものは配布とみなさない）。calshare のようにコードをビルドして Cloudflare Workers（サーバサイド）に配置する行為は「配布」ではなく「実行」に分類されるのが一般的な解釈。**ただし `src/web`（ブラウザに配信する JS）にバンドルしてブラウザへ配信する場合は、利用者の端末にコードを渡す行為であり「配布」に当たる**。この場合は通常のコピーレフトの義務（ソース開示等）が及ぶため、サーバサイド専用の依存と同じ扱いはできない。

- 著作権表示: 必須
- ライセンス同梱: 必須
- 改変の明示: 改変した旨と日付の明記が必要
- 名称の制約: 規定なし
- 特許条項: GPL-3.0 のみ明示（GPL-2.0 にはない）
- **コピーレフトの範囲**: 強い。GPL コードとリンク・結合した成果物全体が GPL の対象になりうる（「配布」する場合）
- ネットワーク配信: GPL 自体にはネットワーク条項がない（AGPL との違い）。SaaS 内部でのみ動かして外部に配布しないなら、開示義務が発生しない可能性が高い
- 商用利用: 可（ただしコピーレフトの範囲内で）
- **弁護士に相談すべき典型例**: GPL/LGPL/AGPL 系コードをサーバサイド（Workers）に組み込む場合、および `src/web` にバンドルしてブラウザへ配信する場合。「配布に当たらない」という整理はプロジェクトの構成次第で崩れうるため、確度が必要なら弁護士確認に回す

## AGPL-3.0

GPL-3.0 に「ネットワーク経由の利用」を配布とみなす条項（第13条）を追加したもの。

- 著作権表示・ライセンス同梱・改変の明示: GPL-3.0 と同様
- 特許条項: あり
- **コピーレフトの範囲**: 最も強い。**ネットワーク越しにサービスとして提供する（SaaS）だけで「配布」とみなされ、対応するソースコード一式をそのサービスの利用者に無償で提供する義務が生じる**
- **calshare のような Cloudflare Workers 上の SaaS に AGPL コードを組み込むと、calshare 自体のソースを公開する義務を負う可能性が高い。取り込みは原則不可、少なくとも判定は弁護士に確認すべき論点として明示する**
- 商用利用: 可（ただし上記の開示義務込みで）

## CC-BY-4.0

画像・アイコン・写真・データセットなどでよく使われる。

- 著作権表示（Attribution）: 必須。著作権者名・出典・ライセンスへのリンク・改変の有無を、合理的な方法で明示する
- ライセンス同梱: 全文同梱は必須ではないが、ライセンスへの参照（URL 等）は必須
- 改変の明示: 改変した場合はその旨を示す
- 名称の制約: 著作権者の推薦を受けたと誤認させる表示は不可
- コピーレフトの範囲: なし（CC-BY-SA と違い派生物に同じライセンスを強制しない）
- 商用利用: 可

## CC0 / Unlicense

パブリックドメイン相当。権利放棄の意思表示であり、法域によっては完全な放棄が認められない場合の保険としてフォールバックの許諾文言が付いている。

- 著作権表示: 不要（ただし出典を書いても問題はない。「不要」であって「禁止」ではない）
- ライセンス同梱: 不要
- 改変の明示: 不要
- 名称の制約: なし
- コピーレフトの範囲: なし
- 商用利用: 可
- 注意点: 「著作権表示が要らない」ことが誤って他のライセンスにも適用されがちなので、必ず対象物のライセンスファイルを個別に確認する

## 判定の付け方（共通の考え方）

1. **著作権表示・ライセンス同梱が要る場合**、calshare での配布先（リポジトリ／R2／ブラウザ配信物）ごとに「どこに何を置くか」を条件に落とす。サーバ側だけで使うなら、リポジトリ内の同梱で足りることが多い。ブラウザに配信する（フォントファイルそのもの、画像そのものを配る）場合は配信物側にも表示が要る場合がある。ブラウザ配信バンドル（`src/web`）に含まれる npm 依存は、minify で個々のコメント・著作権表示が失われやすいので、ライセンス表示を残す設定（esbuild の `legalComments` 等）か、`THIRD-PARTY-NOTICES` のようなファイルを別途配信することで表示義務を満たす
2. **コピーレフト系（MPL/LGPL/GPL/AGPL）**は「改変したか」「静的リンクか動的リンクか」「配布か実行か」の3点で範囲が変わる。npm パッケージを改変せず import するだけなら大半は問題にならないが、calshare は wrangler（esbuild）でバンドルするため LGPL は静的リンク相当と解される余地がある点に注意する。AGPL は実行（SaaS 提供）自体がトリガーになるため別格に扱う
3. 判定に迷う・情報が矛盾する（package.json とリポジトリの LICENSE が食い違う、デュアルライセンスでどちらを選ぶか等）ときは「不可」に倒さず、判定書に「弁護士に相談すべき論点」として明示して次のアクションを止めない

## npm 依存の許容リスト（改変せず import する場合）

`dependency-audit` スキルが依存関係のライセンスをこのリストと照合する。改変せずそのまま import する（バンドルするだけで手を加えない）前提のリストで、リスト外のライセンスはこのファイルの各節に沿って個別に審査する。

`MIT` `ISC` `BSD-2-Clause` `BSD-3-Clause` `Apache-2.0` `0BSD` `CC0-1.0` `Unlicense` `MPL-2.0`（`OR` 区切りのデュアルライセンスはいずれかがこのリストに入っていれば可）

- **MPL-2.0 は「改変しない場合のみ」許容**。MPL 対象ファイルを改変してリポジトリに取り込む場合は、上記「MPL-2.0」節のファイル単位開示義務に従って個別判断する
- リスト外・`license` フィールドが無く LICENSE ファイルも無いものは、手順3（本ファイルの各節）で審査する
