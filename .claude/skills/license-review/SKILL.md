# license-review

外部成果物のライセンス審査を、Issue を起票して終わりにせず「承認できる記録」まで作る。オーナーに残す判断は最終的に「この記録を承認する」の1点にする。

## 審査対象になるもの

npm パッケージ、フォント、画像・アイコン、コード片（Stack Overflow やブログからの引用含む）など、calshare のリポジトリまたは配信物に取り込む外部の成果物すべて。「一部だけコピーして書き換えた」場合も対象（改変は義務を消さない）。

## 手順

### 1. 対象とライセンス本文を特定する

- npm パッケージ: `node_modules/<pkg>/package.json` の `license` フィールドと、パッケージディレクトリ内の `LICENSE` / `LICENSE.md` 系ファイルを見る。`package.json` と `node_modules` があるなら `scripts/npm-licenses.mjs` で直接依存を一括で洗い出せる（下記「スクリプト」参照）。
- フォント: 同梱の `OFL.txt` / `LICENSE` を見る。無ければ配布元（Google Fonts、フォントベンダーの公式サイト等）を WebFetch で確認する。**実際に配置するバイナリの取得元で審査する**（同じフォント名でも配布元によってビルドが異なる場合がある。取得スクリプトがあればその URL・バージョンを審査対象にする）。`LICENSE`/`OFL.txt` に著作権表示・Reserved Font Name（RFN）宣言が含まれない場合は、フォント本体の `name` テーブル（ID 0: Copyright、ID 7: Trademark、ID 13: License Description）を読んで確認する。バイナリを取得できるならこのセッションで取得コマンドを実行して確認まで済ませ、判定を「条件付き可」にして未確認事項を条件に混ぜない。実行できない環境なら判定は保留にし、「未確認の事実」に「name テーブルの確認が不足」と書く。
- 画像・アイコン・コード片: 配布元のライセンス表記（Icon 素材サイトの利用規約、Gist のライセンス欄等）を確認する。表記が見当たらない場合は「ライセンス不明」として扱い、後述の判定に進まず弁護士確認の論点に上げる。

### 2. SPDX 識別子に対応付ける

「MIT License」「The MIT License」「MIT」のような表記ゆれを SPDX 識別子（`MIT`）に正規化する。読み取れたライセンス本文の特徴（章立て、キーワード）が SPDX の定義と一致するか、自己判断で怪しければ本文を引用して確認する。

### 3. 義務を列挙する

`references/licenses.md` に主要なライセンス（OFL-1.1、MIT、ISC、BSD-2/3-Clause、Apache-2.0、MPL-2.0、LGPL-2.1/3.0、GPL-2.0/3.0、AGPL-3.0、CC-BY-4.0、CC0、Unlicense）ごとの義務（著作権表示・ライセンス同梱・改変の明示・名称の制約・特許条項・コピーレフトの範囲・ネットワーク配信の扱い・商用利用）をまとめてある。該当する項を引いて、義務を1つずつ拾う。

### 4. calshare での利用形態を確認し、義務の適用を判定する

次の観点で利用形態を確認する。義務は形態によって適用有無や範囲が変わるので、必ず具体的に当てはめる。

- サーバ側（Cloudflare Workers）でのみ使うか、ブラウザに配信するか
- 改変・サブセット化するか
- リポジトリに同梱するか
- ソースが private か
- **配置先の列挙**: リポジトリ（テスト用フィクスチャを含む）・R2・ブラウザ配信物のそれぞれについて、成果物が置かれる場所ごとにライセンスと著作権表示を同梱する。OFL 条項2のように、義務が「各コピー」に対して課されるライセンスがあるため、1箇所に置けば足りると思い込まない

例えば MIT は利用形態を問わず著作権表示とライセンス同梱が要るが、LGPL は「動的リンク（改変せず import するだけ）」なら自作コード側への波及がない、AGPL は「サーバで動かして公開するだけ」でも開示義務が生じる、のように形態が結論を左右する。

### 5. 判定を出す

**可 / 条件付き可 / 不可** の3値で判定する。条件付きなら、満たすための具体的な作業（ファイル名・同梱先・表示文言）まで書く。「Issue を切って終わり」にせず、次にやる作業が1行ずつ実行可能な形で並ぶまで具体化する。

**事実確認が済んでいない項目は条件に入れない。** 自分で確認できるもの（フォント本体を取得して `name` テーブルを読む、実際のパッケージの LICENSE を開く等）はこのセッションで確認してから判定する。確認手段がこのセッションに無いもの（実機での目視、他者の承認待ち等）だけを「残る判断」として分けて書く。「〇〇を確認すること」を条件付き可の条件に混ぜると、オーナーは実装側の作業と審査の未了事項の区別がつかない。

### 6. 記録する

`docs/licenses/<対象名>.md` に `assets/record-template.md` の形式で記録する。含める項目: ライセンス種別、取得元 URL、バージョン、SHA-256（分かれば）、義務と対応、判定、判定日、審査者（このスキル）。

オーナーに残る判断は「この記録を承認する」だけにする。次のいずれかに該当するときは、判定を保留せず「弁護士に相談すべき論点」として明示した上で記録を進める（判断の放棄はしない。何が論点で、なぜ一エンジニアの判断を超えるかを書く）。

- コピーレフトの強いライセンス（GPL・AGPL 系）のコードをサーバサイドに取り込む
- ライセンスが不明、または表記が矛盾している
- デュアルライセンスでどちらを適用するか選択の余地がある

## スクリプト: npm 依存のライセンス一覧

```
node .claude/skills/license-review/scripts/npm-licenses.mjs
```

カレントディレクトリの `package.json` と `node_modules` を見て、直接依存（`dependencies` + `devDependencies`）ごとに `name` / `version` / `package.json` の `license` / `LICENSE` ファイル同梱有無を Markdown テーブルで出す。`package.json` または `node_modules` が無ければその旨を出して終了するので、その場合は手順(1)を手動で行う。出力はそのまま手順(3)〜(6)の入力に使える。

このスクリプトは Node 20 標準ライブラリのみで書かれている。テストは `node --test .claude/skills/license-review/scripts/npm-licenses.test.mjs`。

## 例

- `references/example-noto-sans-jp.md`: OGP 画像描画用フォント Noto Sans JP（OFL-1.1）の審査例。サブセット化して Cloudflare R2 に置き、Workers 内の描画にだけ使い、ブラウザには PNG しか配信しない、という calshare 特有の利用形態を手順(1)〜(6)に当てはめている。新しい対象を審査する前にこの例を読むと、判定書の粒度が揃う。

## 出力フォーマット

判定の要点をチャットで報告するときは、次の順で簡潔にまとめる（詳細は記録ファイルに書く）。

```
対象: <対象名>（<SPDX識別子>）
判定: 可 / 条件付き可 / 不可
根拠: <references/licenses.md のどの義務が効いたか、1〜3行>
残る条件（条件付きの場合。実装側の作業）: <具体的な作業>
未確認の事実（あれば。誰がどう確認するか）: <このセッションで確認できなかった事実と、確認の担当・方法>
次のアクション: <この記録を受けて次に誰が何をするか>
記録: docs/licenses/<対象名>.md に保存済み
オーナーへの依頼: この記録の承認のみ / 弁護士確認が必要な論点あり（内容）
```
